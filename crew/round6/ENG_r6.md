## 1. 移植内容（相对分支原样的改动）
- 取 `origin/feat/quality-pass:units/sprite.py`（R1 包围盒 ROI 合成 + R2 线性基底缓存 + 同 PNG 预处理进程内共享）。
- `SPRITE_FAST` 默认先 `0`（分支是 1）。
- 三处缓存键（wind / _front / 线性基底）补 `id(A)`、`id(ring)`、`id(wind_w)`：main 各组有「改 sp.A / sp.ring 再画」写法（b_kit、chorus1_sprites、sec_d_bridge、sec_b_verse2），分支原键只认 id(F)，会命中旧结果。
- `_support()` 的 `is not` 比整数改 `!=`（分支注释里已知的小 bug，只影响速度）。
- 内存：分支 `_SCACHE` 上限 32 条整幅精灵（每条 ~100MB）→ 改为只在 FAST 回退路径缓存、上限 4；`_WCACHE` 上限 2。原因：全片冒烟时单进程跑到副歌一被系统 Killed（疑似内存），FAST=0 也不再比旧 main 多占内存。
- **main 新增用法兼容**：B1 #15 唇红（`sec_b_pre1.py:569/898`）把 `keep_red` 传成精灵空间逐像素数组 `self.kr`，分支版 `float(keep_red)` 直接崩（50.9s TypeError）。改为：数组 keep_red 在线性基底里按裁剪窗口相乘、缓存键用数组身份；调色参数若是逐像素数组则退回整幅精灵空间路径。

## 4. 全片渲染耗时预估（7240 帧，`tools/render_film.sh`）
- FAST=1：约 2.2 s/帧 × 7240 ≈ 4.4 小时（单渲染位）；2 个渲染位都空时约 2.2–2.5 小时。
- FAST=0 对照：C18 一镜（28 帧）多约 17 分钟，其余用精灵的帧每帧多约 1 s（约 4600 帧）→ 单位多约 1.3–1.5 小时。
- 粗估，按单帧冷启动数推算；实际分块连续渲染缓存更热，可能更快。另两组同时占渲染位时按比例拉长。

## 5. 风险 / 留意
- 同一 PNG 的 A/F/ring 数组在进程内**共享只读**。目前 main 对精灵只有「整体重新赋值」写法；以后若有人写 `sp.A *= …` / `sp.A[...] = …` 这类**原地改**，会串到同图其它实例。已核过的原地写（c_kit 281/380、sec_a 302/2032/2890、sec_c 167/234/2278/2291）都是文字层 `T.Layer`，不是精灵。
- 回滚：`SPRITE_FAST=0` 即旧实现（逐像素同旧 main）。
- 没动：`units/subtitle.py`、`units/a_kit.py`、任何段落文件。
